# Purpose

Define the provider-neutral contracts, ownership boundaries, and privacy rules for Jarvis home-specific knowledge before any storage, ingestion, or retrieval implementation begins.

## Approval Status

Approved. The six decisions in this document are the governing architecture for the Knowledge Engine's initial implementation milestones.

# Background

Jarvis needs dependable reference information about a particular home that is neither live Home Assistant state nor personal memory. Examples include a room's documented layout, a device manual supplied by the household, a maintenance procedure, or an approved project note. This knowledge should give later orchestration useful local reference material without duplicating Home Assistant, reimplementing language-model general knowledge, or silently turning user conversations into a knowledge base.

EPIC 2 Memory stores explicit, user-relevant preferences, facts, instructions, and projects. EPIC 3 Knowledge stores curated, home-specific reference material. The systems can both be relevant to a request, but they require separate contracts, policies, and lifecycle rules.

# Proposed Architecture

## Ownership Boundaries

| Owner | Responsibility | Not owned by Knowledge Engine |
| --- | --- | --- |
| Home Assistant | Devices, entities, automations, integrations, configuration, and current or historical state. | Copying or caching Home Assistant state, entity registries, service definitions, or history. |
| Language model | General knowledge, reasoning, language, planning, and document interpretation. | Being replaced by a Jarvis general-knowledge corpus or ranking engine. |
| Memory subsystem | Explicit, user-relevant durable preferences, facts, instructions, and projects. | Reclassification of personal memory as knowledge to bypass memory consent. |
| Knowledge Engine | Curated, home-specific reference content approved for Jarvis use. | Live state, event history, automatic conversation capture, inferred information, and device control. |

Knowledge remains optional. A request can be assembled and executed without a knowledge provider or matching knowledge record.

## Initial Taxonomy

| Type | Purpose | Initial release |
| --- | --- | --- |
| `HOME_REFERENCE` | Stable, curated reference material about the home as a whole. | Eligible with explicit approval. |
| `ROOM_DOCUMENTATION` | Human-provided room, area, or layout documentation. | Eligible with explicit approval. |
| `DEVICE_DOCUMENTATION` | User-approved manuals, instructions, or maintenance notes for a device. | Eligible with explicit approval; must not duplicate live HA state. |
| `HOUSEHOLD_PROCEDURE` | Approved repeatable household procedure, such as maintenance guidance. | Eligible with explicit approval. |
| `PROJECT_DOCUMENTATION` | Curated reference material for an ongoing home project. | Eligible with explicit approval. |
| `USER_APPROVED_REFERENCE` | Other explicitly approved home-specific material that fits no initial type. | Eligible with explicit approval. |

Knowledge records do not contain complete conversation transcripts, Home Assistant event history, inferred observations, automatic summaries, or general encyclopedia-style information.

## Record Contract

The proposed provider-neutral `KnowledgeRecord` contract is:

```python
class KnowledgeType(str, Enum):
    HOME_REFERENCE = "home_reference"
    ROOM_DOCUMENTATION = "room_documentation"
    DEVICE_DOCUMENTATION = "device_documentation"
    HOUSEHOLD_PROCEDURE = "household_procedure"
    PROJECT_DOCUMENTATION = "project_documentation"
    USER_APPROVED_REFERENCE = "user_approved_reference"


class KnowledgeSource(str, Enum):
    USER_PROVIDED = "user_provided"
    USER_APPROVED_DOCUMENT = "user_approved_document"
    USER_APPROVED_IMPORT = "user_approved_import"


class KnowledgeStatus(str, Enum):
    ACTIVE = "active"
    PENDING_APPROVAL = "pending_approval"
    REJECTED = "rejected"


@dataclass(frozen=True, slots=True)
class KnowledgeRecord:
    knowledge_id: str
    knowledge_type: KnowledgeType
    content: str
    source: KnowledgeSource
    created_at: datetime
    updated_at: datetime
    source_request_id: str | None = None
    title: str | None = None
    tags: tuple[str, ...] = ()
    status: KnowledgeStatus = KnowledgeStatus.ACTIVE
    metadata: Mapping[str, object] = field(default_factory=dict)
```

`knowledge_id` is opaque and unique. `source_request_id` provides request correlation without copying the source conversation. `metadata` is limited to non-content, provider-neutral attributes; it must not become a way to store hidden source material, Home Assistant state, credentials, or user memory.

Initial active records are durable until explicitly corrected, replaced, or hard-deleted. A correction replaces the current content without retaining prior values. Hard deletion removes content and metadata without a tombstone. `PENDING_APPROVAL` and `REJECTED` are contracts reserved for a future approved ingestion workflow; no unapproved content is persistently stored in M3.1.

## Explicit Ingestion and Privacy

Initial knowledge ingestion must be explicit and user-approved. A caller must name the content or document and request that it become Jarvis knowledge. Jarvis must not scrape documents, import Home Assistant configuration or history, extract knowledge from conversations, or infer home facts automatically.

Knowledge is not a privacy bypass for Memory. Personal preferences, household facts about people, instructions directed at Jarvis, and project information that is user-relevant belong in Memory unless a later approved policy explicitly defines a different category. Sensitive or personal material must not be stored as Knowledge merely because it appears in a reference document. The initial release rejects sensitive knowledge rather than adding a confirmation flow; any future sensitive-knowledge policy requires a separate decision.

## Provider-Neutral Interfaces

The initial interface boundaries are:

- `KnowledgeStore`: physical persistence only. It creates, gets, lists, updates, hard-deletes, clears, and checks records without making policy or relevance decisions.
- `KnowledgePolicy`: decides explicit approval, allowed source and type, privacy eligibility, and retrieval eligibility.
- `KnowledgeWriter`: creates, corrects, and replaces records only after policy approval.
- `KnowledgeRetriever`: reads policy-eligible records using a deterministic query and returns provider-neutral matches without writing storage.
- `KnowledgeContextProvider`: depends only on `KnowledgeRetriever` and converts approved results to a bounded typed knowledge section in `ContextPackage`.

No interface may depend directly on a concrete backend, Home Assistant client, language-model provider, ConversationManager, vector store, or embedding provider.

## Initial Retrieval and Context Use

The first retrieval implementation should mirror the safety posture of Memory without reusing its personal-memory contract. It may support exact normalized text, explicit type, and tag filters with deterministic ascending identifier ordering. It must not use embeddings, vector databases, fuzzy matching, semantic search, LLM ranking, or automatic query expansion.

Context Assembly may consume a future typed `KnowledgeContext` through `KnowledgeContextProvider`. That provider supplies the original request text, a bounded result limit, and default privacy-safe settings to `KnowledgeRetriever`. It must not access `KnowledgeStore` directly, rerank matches, invoke Home Assistant, or contact an LLM.

The initial proposed Context contract includes only curated content, title, type, tags, source category, and deterministic retrieval score. It excludes opaque identifiers, request correlations, raw timestamps, status, internal metadata, and ranking diagnostics.

# Functional Requirements

- Define `KnowledgeRecord`, `KnowledgeType`, `KnowledgeSource`, and `KnowledgeStatus` contracts.
- Define provider-neutral store, policy, writer, retriever, and context-provider responsibilities.
- Require explicit user approval before any initial knowledge persistence.
- Reject sensitive, inferred, automatically extracted, Home Assistant-derived, and unsupported-source knowledge in the initial release.
- Preserve source and request correlation without retaining full conversations or source-document duplicates.
- Define correction, replacement, inspection, and hard-deletion expectations.
- Specify deterministic, non-semantic initial retrieval boundaries.
- Specify typed, bounded Context Assembly consumption without a concrete backend dependency.

# Acceptance Criteria

- The Knowledge Engine has a contract distinct from Memory, Home Assistant, and language-model general knowledge.
- A knowledge record supports identity, taxonomy, provenance, status, explicit approval, correction, and hard deletion.
- Policy boundaries prevent automatic, inferred, sensitive, and Home Assistant-derived knowledge ingestion.
- The proposed store can be replaced without changing writer, retrieval, or Context Assembly contracts.
- Retrieval and context use are provider-neutral, deterministic, bounded, and non-semantic.
- No M3.1 artifact implements storage, ingestion, retrieval, Context Assembly integration, Home Assistant integration, language-model interaction, or document parsing.

# Out of Scope

- Production models, databases, files, document parsing, import connectors, and persistent storage.
- Home Assistant configuration, entity, device, service, automation, state, or history import.
- Automatic web, document, conversation, or event ingestion.
- Embeddings, vector databases, semantic or fuzzy search, LLM ranking, and automatic query expansion.
- Sensitive-knowledge confirmation, encryption, multi-user ownership, audit logging, UI flows, and natural-language intent detection.
- Changes to Memory, Context Assembly, Execution Pipeline, Response Pipeline, Home Assistant, or ConversationManager.

# Approved Decisions

1. Knowledge is curated home-specific reference material, distinct from Memory, Home Assistant state, event history, and general language-model knowledge.
2. The initial taxonomy and explicitly approved source categories are approved.
3. Sensitive knowledge is rejected rather than stored pending confirmation.
4. Correction replaces content and deletion is hard deletion, with no historical content retention.
5. Initial retrieval is deterministic exact text/type/tag matching only, with no semantic or automated retrieval mechanisms.
6. Context Assembly will consume typed, bounded knowledge only through `KnowledgeRetriever`.
