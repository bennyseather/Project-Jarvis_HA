# Purpose

Define the policy-controlled path for explicitly approved Knowledge creation and correction, while keeping storage, document handling, retrieval, and Context Assembly separate.

## Implementation Status

Approved and implemented. Knowledge creation and correction are policy-controlled, explicit, non-sensitive, and storage-provider-neutral.

# Background

M3.1 defines Knowledge as curated home-specific reference material and M3.2 provides storage mechanics. M3.3 introduces the boundary that decides whether a proposed record is appropriate to persist and coordinates only approved writes through `KnowledgeStore`.

Knowledge must not become a way to store live Home Assistant state, general language-model knowledge, personal memory, inferred observations, or unapproved document content. A caller must make a typed, explicit approval request before any knowledge is stored.

# Proposed Architecture

## Contracts

Define these provider-neutral contracts in a dedicated knowledge-writing model module:

```python
class KnowledgePolicyDecision(str, Enum):
    APPROVED = "approved"
    REJECTED = "rejected"
    REQUIRES_CONFIRMATION = "requires_confirmation"


class KnowledgeWriteStatus(str, Enum):
    CREATED = "created"
    UPDATED = "updated"
    REJECTED = "rejected"
    REQUIRES_CONFIRMATION = "requires_confirmation"
    FAILED = "failed"


@dataclass(frozen=True, slots=True)
class ExplicitKnowledgeWriteRequest:
    content: str
    knowledge_type: KnowledgeType
    source: KnowledgeSource
    source_request_id: str | None = None
    title: str | None = None
    tags: tuple[str, ...] = ()
    metadata: Mapping[str, object] = field(default_factory=dict)
    is_explicitly_approved: bool = True
    is_sensitive: bool = False


@dataclass(frozen=True, slots=True)
class KnowledgeCorrectionRequest:
    target_knowledge_id: str
    replacement_content: str
    source: KnowledgeSource
    source_request_id: str | None = None
    title: str | None | UnsetType = UNSET
    tags: tuple[str, ...] | UnsetType = UNSET
    metadata: Mapping[str, object] | UnsetType = UNSET
    is_explicitly_approved: bool = True
    is_sensitive: bool = False


@dataclass(frozen=True, slots=True)
class KnowledgePolicyResult:
    decision: KnowledgePolicyDecision
    reason_code: str


@dataclass(frozen=True, slots=True)
class KnowledgeWriteResult:
    status: KnowledgeWriteStatus
    reason_code: str
    record: KnowledgeRecord | None = None
    requires_confirmation: bool = False
```

Use the existing public `UNSET` pattern from Memory for all optional correction fields. `UNSET` preserves the current field; any provided value replaces it; explicit `None` clears nullable fields; empty collections replace current collections with empty values.

## KnowledgePolicy

Introduce a `KnowledgePolicy` protocol with separate creation and correction evaluation methods. Its initial deterministic implementation, `ExplicitKnowledgePolicy`, approves only requests that meet every condition:

- `is_explicitly_approved=True`.
- An allowed initial `KnowledgeType`.
- An allowed source: `USER_PROVIDED`, `USER_APPROVED_DOCUMENT`, or `USER_APPROVED_IMPORT`.
- Non-sensitive content (`is_sensitive=False`).
- A record that represents curated, home-specific reference material as asserted by the typed caller.

The policy rejects inferred, automatic, unsupported-source, Home Assistant-derived, general-knowledge, personal-memory, and sensitive requests. The initial contract does not attempt natural-language classification of those categories; the typed caller is responsible for setting the request fields, while later orchestration may validate them through an approved capability.

`REQUIRES_CONFIRMATION` is reserved for a future sensitive-knowledge policy and is not emitted by the initial implementation. Sensitive content is rejected without persistence.

## KnowledgeWriter

Define a `KnowledgeWriter` protocol with `create_explicit_knowledge` and `correct_knowledge` methods. `PolicyControlledKnowledgeWriter` depends only on `KnowledgeStore`, `KnowledgePolicy`, `KnowledgeRecordFactory`, and an injectable timestamp source.

Creation evaluates policy before constructing or storing a record. Correction reads the target record, evaluates policy, then creates a replacement that preserves `knowledge_id` and `created_at`, sets `updated_at`, and replaces the prior content. Neither operation retains prior content or creates a hidden parallel record.

Duplicate content is permitted in the initial release. Storage identity is `knowledge_id`, while two separately approved records may legitimately share content but differ in source, title, scope, tags, or later lifecycle. Deduplication requires a future explicit policy decision and must not be silently inferred by the writer.

## Future Document-Import Boundary

A later document-import capability may parse an explicitly selected source outside `KnowledgeWriter`, present its proposed content and provenance to the user, and then submit one or more `ExplicitKnowledgeWriteRequest` values only after explicit approval. `KnowledgeWriter` must receive final typed content only; it does not parse files, access file systems, discover documents, or import data on its own.

# Functional Requirements

- Define typed creation, correction, policy, and write-result contracts.
- Define provider-neutral `KnowledgePolicy` and `KnowledgeWriter` protocols.
- Approve only explicitly approved, non-sensitive requests with allowed types and sources.
- Reject inferred, automatic, unsupported-source, Home Assistant-derived, general-knowledge, personal-memory, and sensitive requests without storage mutation.
- Preserve provenance and source-request correlation for approved writes.
- Correct records by preserving identity and creation time while replacing current content and mutable fields.
- Implement documented `UNSET` behavior for correction fields.
- Keep duplicate content permitted unless identifiers collide.

# Acceptance Criteria

- Approved explicit knowledge is stored with deterministic identity and timestamps.
- Rejected and invalid operations do not mutate `KnowledgeStore`.
- Corrections preserve `knowledge_id` and `created_at` while replacing prior content.
- Omitted, replaced, cleared, and emptied correction fields follow the documented `UNSET` semantics.
- Duplicate identifiers produce a focused failure outcome; duplicate content remains valid.
- No document parsing, file import, automatic extraction, Home Assistant call, LLM call, retrieval, ranking, Context Assembly integration, or sensitive persistence is implemented.

# Out of Scope

- Document/file parsing, import connectors, filesystem access, and user-interface approval flow.
- Natural-language classification or automated identification of sensitive, personal-memory, or Home Assistant-derived content.
- Retrieval, ranking, semantic search, embeddings, Context Assembly integration, inspection, management, deletion, encryption, multi-user ownership, audit logging, EventBus, Home Assistant, LLM, and ConversationManager changes.

# Dependencies

- M3.1 Knowledge Contracts and Boundaries.
- M3.2 In-Memory Knowledge Store.
- ADR-001 Project Scope.
- EPIC 2 Memory policy and writer patterns.

# Approved Decisions

1. Explicit user approval is the only initial Knowledge-write authorization.
2. Sensitive Knowledge is rejected rather than stored pending confirmation.
3. Approved sources and types are the initial eligibility boundary.
4. Corrections replace content without history and use documented `UNSET` semantics.
5. Duplicate content is valid while duplicate identifiers are rejected.
6. A future document-import flow supplies explicitly approved typed requests without giving `KnowledgeWriter` parsing or import authority.
