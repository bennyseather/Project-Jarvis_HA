# Purpose

Define deterministic, provider-neutral retrieval of policy-eligible curated Knowledge without writing records, parsing documents, or integrating with Context Assembly.

## Implementation Status

Approved and implemented. Retrieval is policy-controlled, deterministic, bounded, and independent of Context Assembly.

# Background

M3.1 through M3.3 establish explicitly approved Knowledge contracts, in-memory storage, and policy-controlled writing. M3.4 makes approved reference material available to a later orchestration stage through deterministic filtering and ranking. It does not decide what content may be written, create knowledge automatically, or make a request context depend on knowledge.

# Proposed Architecture

## Contracts

```python
@dataclass(frozen=True, slots=True)
class KnowledgeRetrievalQuery:
    query_text: str = ""
    requested_knowledge_types: frozenset[KnowledgeType] = frozenset()
    requested_tags: tuple[str, ...] = ()
    maximum_results: int = 5
    metadata: Mapping[str, object] = field(default_factory=dict)


@dataclass(frozen=True, slots=True)
class KnowledgeMatch:
    record: KnowledgeRecord
    total_score: float
    score_breakdown: Mapping[str, float]
    matched_reasons: tuple[str, ...]


@dataclass(frozen=True, slots=True)
class KnowledgeRetrievalResult:
    matches: tuple[KnowledgeMatch, ...]
    eligible_records_considered: int
    records_excluded_by_policy: int
    query_metadata: Mapping[str, object] = field(default_factory=dict)
```

`maximum_results` defaults to 5, must be between 0 and 10 inclusive, and returns no matches without ranking when zero. Empty query text and empty type/tag filters are valid and return ordered policy-eligible records. Type filters use membership; tag filters use normalized, casefolded, whitespace-collapsed match-any behavior.

## Policy and Provider Boundaries

Introduce a `KnowledgePolicy.evaluate_retrieval(record, query)` method and a typed eligibility result. The initial policy admits only `ACTIVE` records with an approved Knowledge type and source. It rejects pending, rejected, malformed, or otherwise policy-ineligible records before filtering or ranking.

Introduce `KnowledgeRetriever` and `PolicyControlledKnowledgeRetriever`. The retriever depends only on `KnowledgeStore`, `KnowledgePolicy`, `KnowledgeRanker`, and an optional deterministic metadata/time source. It executes this fixed order:

1. Read defensive copies from `KnowledgeStore`.
2. Apply policy eligibility.
3. Apply type and tag filters.
4. Rank remaining records.
5. Limit the ordered results.

It must never write, update timestamps, delete records, parse documents, invoke Home Assistant, call an LLM, or access Context Assembly.

## Deterministic Ranking

Normalize query text, content, titles, and tags with Unicode casefolding, trimming, and internal whitespace collapse. Tokens are unique, whitespace-delimited token sets. No stemming, synonyms, fuzzy matching, embedding, semantic search, or language-model processing is permitted.

| Signal | Score |
| --- | --- |
| Exact normalized content match | +5.0 |
| Exact normalized title match | +3.0 |
| Content token overlap | shared unique query/content tokens ÷ unique query tokens × 4.0 |
| Title token overlap | shared unique query/title tokens ÷ unique query tokens × 2.0 |
| Requested-tag overlap | matching requested tags ÷ unique requested tags × 2.0 |

Exact and token-overlap scores may both apply. Missing titles contribute zero title score. Empty query text contributes zero text-related signals. The total is the unrounded sum of the inspectable score breakdown. Matches sort by total score descending, then `knowledge_id` ascending.

Knowledge type is deliberately a hard filter rather than a ranking signal. Source, timestamps, status, metadata, and request correlation are not ranking signals.

# Functional Requirements

- Define typed Knowledge retrieval query, eligibility, match, and result contracts.
- Define provider-neutral `KnowledgeRetriever` and `KnowledgeRanker` protocols.
- Implement policy-controlled deterministic reference retrieval.
- Filter policy-ineligible, type-filtered, and tag-filtered records before ranking.
- Expose every ranking signal in a deterministic score breakdown.
- Enforce a default result limit of five and hard maximum of ten.
- Return defensive-copy records and never mutate storage.
- Define invalid-query validation for limits and malformed filter values.

# Acceptance Criteria

- Active, policy-eligible records can be retrieved through provider-neutral contracts.
- Ineligible records do not reach ranking.
- Exact content, title, token, tag, empty-query, filter, limit, and identifier tie-break behavior are deterministic.
- Returned matches cannot mutate store-held records.
- Empty and zero-limit retrieval results are defined and safe.
- Retrieval performs no writes, timestamp changes, document parsing, Home Assistant call, LLM call, Context Assembly integration, embedding, vector search, semantic search, fuzzy matching, or automatic query expansion.

# Out of Scope

- Knowledge Context Assembly integration.
- Knowledge creation, correction, deletion, inspection, management, document parsing, and import connectors.
- Home Assistant state, configuration, or history access.
- Embeddings, vector databases, semantic or fuzzy search, LLM ranking, and automatic query expansion.
- Persistent storage, encryption, multi-user ownership, audit logging, EventBus, ConversationManager, and response changes.

# Dependencies

- M3.1 Knowledge Contracts and Boundaries.
- M3.2 In-Memory Knowledge Store.
- M3.3 Explicit Knowledge Approval and Writing.
- ADR-001 Project Scope.

# Approved Decisions

1. Eligibility is limited to active records with approved Knowledge type and source.
2. The default result limit is five and the hard maximum is ten.
3. Ranking uses the documented deterministic formula and ascending opaque identifier tie-breaker.
4. Empty queries retrieve policy-eligible records in deterministic order.
5. Semantic, fuzzy, vector, embedding, and LLM-assisted retrieval are excluded.
