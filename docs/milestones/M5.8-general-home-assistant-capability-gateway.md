# Purpose

Give Jarvis access to Home Assistant's available capabilities through one general, policy-controlled gateway instead of hard-coding device domains one at a time.

# Architecture

Home Assistant remains the system of record and executor. Jarvis discovers its currently available services, validates a language-model proposal against that live capability information, applies local risk policy, requests confirmation where required, and only then invokes Home Assistant.

```text
Home Assistant live services and entities
  -> Capability Gateway discovery cache
  -> LLM typed action proposal
  -> Jarvis schema and authorization validation
  -> risk classification and confirmation policy
  -> Home Assistant service execution
  -> structured outcome
```

The language model never receives credentials and never calls Home Assistant directly.

# Provider Contracts

- `HomeAssistantCapabilityProvider`: discovers services, domains, service fields, and current entity metadata from Home Assistant.
- `HomeAssistantActionProposal`: contains domain, service, validated target/entity references, service data, and a human-readable action summary.
- `HomeAssistantCapabilityGateway`: resolves entities, validates service existence and service data, applies authorization and risk policy, creates pending confirmations, and invokes one typed Home Assistant service operation only after approval.
- `HomeAssistantRiskPolicy`: classifies each validated operation as `READ_ONLY`, `CONFIRM_REQUIRED`, `HIGH_IMPACT_CONFIRM_REQUIRED`, or `FORBIDDEN`.
- `PendingActionStore`: stores one-time, expiry-bound confirmations in process memory.

## Discovery

The gateway retrieves available Home Assistant services and entity metadata from Home Assistant at startup and refreshes them explicitly or after a defined short interval. Jarvis does not maintain a competing device or service registry; discovery data is an operational cache of Home Assistant-owned data.

If service schemas are unavailable, Jarvis must fail closed for state-changing proposals. Read-only state queries remain separately supported through the M5.1 path.

## Validation

Before any service call, the gateway verifies:

- Requested domain and service exist in Home Assistant's currently discovered service catalog.
- Target entities exist and are authorized by policy.
- Service-data keys and primitive values match the discovered service schema where Home Assistant exposes it.
- No credentials, arbitrary templates, scripts, shell commands, URLs, or unknown fields are supplied unless a future explicitly approved policy permits them.
- The proposed action has a deterministic human-readable summary for confirmation.

## Risk Policy

Initial policy classification is deny-by-default:

| Category | Examples | Behavior |
| --- | --- | --- |
| Read-only | State lookup, supported information query | Execute through read-only path. |
| Confirmation required | Lights, switches, climate, covers, media, scenes | Exact one-time confirmation required. |
| High-impact confirmation | Locks, alarms, security systems, garage doors, scripts, automations, system controls | Explicit high-impact confirmation with action summary required. |
| Forbidden | Unknown services, developer/system administration, unsafe payloads, unvalidated schema | Never execute. |

The actual initial domain/service table must be configuration-driven and auditable. A missing classification is `FORBIDDEN`, not confirmation-required.

## Confirmation

Every state-changing action uses a process-local, single-use, expiring token bound to its canonical action payload, target entities, risk category, and user-visible summary. Any alteration, expiry, repetition, or unknown token is rejected. High-impact actions require an explicit confirmation phrase in addition to the token; the first implementation may represent that phrase as a typed confirmation field rather than a natural-language parser.

# Functional Requirements

- Define provider-neutral discovery, proposal, validation, risk, pending-action, and execution-result contracts.
- Discover Home Assistant service and entity capabilities without duplicating ownership.
- Validate every state-changing proposal before confirmation or execution.
- Use configurable domain/service/entity authorization and deny by default.
- Require one-time confirmation for every state-changing action.
- Provide stronger high-impact confirmation requirements.
- Return structured unsupported, forbidden, confirmation-required, unavailable, failed, and successful outcomes.
- Use fakes for all tests; no live Home Assistant operation during tests.

# Acceptance Criteria

- New Home Assistant domains/services can be supported through discovery and configuration rather than Jarvis code changes.
- Unknown, unclassified, or schema-invalid actions never invoke Home Assistant.
- Every state-changing action has an exact, human-readable confirmation summary.
- Entity, service, and data changes invalidate the pending confirmation.
- The gateway has no direct LLM, credential, or presentation dependency.
- The existing read-only assistant path remains available and unchanged.

# Out of Scope

- Autonomous actions, bulk actions, schedules, background execution, voice confirmation, natural-language security verification, arbitrary templating, scripts, shell commands, URL fetching, custom component installation, Home Assistant administration, and privilege management.

# Approval Decisions Required

1. Approve general Home Assistant capability discovery with Home Assistant retained as the source of truth.
2. Approve deny-by-default authorization and risk policy for every domain/service/entity combination.
3. Approve confirmation for all state changes and stronger confirmation for high-impact actions.
4. Approve forbidden treatment for unclassified, schema-invalid, administrative, template/script, or unknown actions.
5. Approve configuration-driven authorization and risk tables rather than one hard-coded light capability.
