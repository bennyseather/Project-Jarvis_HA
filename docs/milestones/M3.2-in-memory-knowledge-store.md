# Purpose

Implement a deterministic, provider-neutral in-memory reference backend for the approved Knowledge Engine contracts.

## Implementation Status

Approved and implemented. The reference provider is process-local, deterministic, mutation-safe, and limited to storage mechanics.

# Background

M3.1 defines Knowledge as curated, explicitly approved home-specific reference material. M3.2 provides only the storage mechanics needed by later policy, writer, retrieval, and Context Assembly milestones. It must not decide whether knowledge is eligible, interpret a document, retrieve relevance, or integrate with Home Assistant.

# Proposed Architecture

## Contracts

Implement the approved `KnowledgeType`, `KnowledgeSource`, `KnowledgeStatus`, and `KnowledgeRecord` contracts in `jarvis.models.knowledge`.

Add an injectable `KnowledgeRecordFactory` that supplies deterministic identifiers and timestamps for tests. The factory creates a record with the same timestamp for `created_at` and `updated_at`.

Define a provider-neutral `KnowledgeStore` protocol with:

- `create(record) -> KnowledgeRecord`
- `get(knowledge_id) -> KnowledgeRecord`
- `list_records() -> tuple[KnowledgeRecord, ...]`
- `update(record) -> KnowledgeRecord`
- `delete(knowledge_id) -> None`
- `clear() -> None`
- `exists(knowledge_id) -> bool`

Define focused store exceptions for duplicate identifiers, missing records, and invalid storage operations. They may be Knowledge-specific equivalents of the existing memory-store exceptions; do not reuse Memory types or make Knowledge depend on Memory.

## In-Memory Reference Provider

Implement `InMemoryKnowledgeStore` in `jarvis.knowledge.in_memory_store`.

- Retain records only for the current process.
- Reject duplicate identifiers rather than overwriting a record.
- Return records in ascending `knowledge_id` order.
- Return defensive copies from every public operation.
- Replace the complete current record on update without retaining prior content or metadata.
- Hard-delete the complete record on delete and clear without tombstones, audit entries, or recoverable references.
- Validate only storage invariants: record type, non-blank identifier and content, valid enum values, and supported basic field shapes. Do not evaluate source approval, sensitivity, Home Assistant ownership, or retrieval relevance.

# Functional Requirements

- Provide typed record, taxonomy, source, status, and factory contracts.
- Provide provider-neutral storage interface and focused exceptions.
- Provide deterministic in-memory create, get, list, update, delete, clear, and exists operations.
- Ensure callers cannot mutate records retained by the store.
- Preserve hard-delete and replacement-without-history behavior.
- Keep all policy, ingestion, document parsing, retrieval, ranking, and Context Assembly behavior out of this milestone.

# Acceptance Criteria

- Records can be created, retrieved, listed, updated, deleted, cleared, and checked for existence.
- Duplicate creates and missing-record operations raise focused exceptions.
- Listing is ascending by `knowledge_id`.
- Callers cannot mutate store-held content or metadata through returned records.
- Updates replace earlier values and hard deletion removes all backend-held references.
- No external service, file, database, Home Assistant integration, language model, policy decision, document parser, ranking, or Context Assembly integration is added.

# Out of Scope

- KnowledgePolicy, KnowledgeWriter, ingestion approval, sensitivity classification, document parsing, import connectors, and retrieval.
- Embeddings, vector databases, semantic search, LLM ranking, and automatic knowledge extraction.
- Persistent storage, encryption, multi-user ownership, audit logging, EventBus integration, Home Assistant, and ConversationManager changes.

# Dependencies

- M3.1 Knowledge Contracts and Boundaries.
- ADR-001 Project Scope.

# Approved Decisions

1. `InMemoryKnowledgeStore` is the first deterministic reference backend.
2. Storage invariants remain separate from policy and ingestion decisions.
3. Listing uses ascending opaque identifiers for deterministic order.
4. Returned records are defensive copies; updates replace prior values and deletion is hard deletion without tombstones.
