# Purpose

Define the explicit, policy-controlled management operations that allow a user to inspect, correct, and hard-delete durable Jarvis memory.

## Implementation Status

Approved and implemented. `PolicyControlledMemoryManager` resolves explicit management targets through `MemoryPolicy` and requests physical deletion only through `MemoryStore`. It uses opaque confirmation tokens to prevent a confirmation from deleting a scope that changed after the original request.

# Background

M2.1 through M2.5 establish memory contracts, in-memory storage, explicit writing, deterministic retrieval, and Context Assembly integration. `MemoryStore` already exposes physical `delete` and `clear` operations, but there is no provider-neutral orchestration contract for locating an explicit management target, preventing ambiguous deletion, or reporting a privacy-safe outcome.

M2.6 supplies that management boundary. It does not add natural-language interpretation; a future orchestration capability must convert an explicit user request into the typed management contracts defined here.

# Proposed Architecture

## Management Boundary

Introduce a provider-neutral `MemoryManager` protocol that depends on `MemoryStore`, `MemoryPolicy`, and the existing `MemoryWriter`:

```text
explicit management request
  -> MemoryManager resolves candidates deterministically
  -> MemoryPolicy authorizes inspection or deletion
  -> MemoryStore hard-deletes exact approved records
  -> MemoryManagementResult reports a non-content outcome
```

`MemoryManager` owns target resolution, ambiguity handling, confirmation state, and structured outcomes. It must not own storage, ranking, lifecycle mutation, or natural-language parsing.

`MemoryStore` remains the only component that physically deletes records. `MemoryWriter.correct_memory` remains the only correction path; M2.6 reuses it rather than duplicating correction behavior. `MemoryRetriever` remains for contextual relevance, not management-target selection.

## Typed Contracts

The proposed contracts are:

```python
class MemoryManagementAction(str, Enum):
    INSPECT = "inspect"
    LIST = "list"
    FIND = "find"
    DELETE_ONE = "delete_one"
    DELETE_MATCHES = "delete_matches"
    DELETE_ALL = "delete_all"


class MemoryManagementStatus(str, Enum):
    SUCCESS = "success"
    NO_MATCH = "no_match"
    REQUIRES_CONFIRMATION = "requires_confirmation"
    REJECTED = "rejected"
    FAILED = "failed"
    PARTIAL = "partial"


@dataclass(frozen=True, slots=True)
class MemoryManagementQuery:
    memory_id: str | None = None
    exact_content: str | None = None
    memory_types: frozenset[MemoryType] = frozenset()
    tags: tuple[str, ...] = ()
    maximum_results: int = 10
    include_sensitive: bool = False


@dataclass(frozen=True, slots=True)
class MemoryManagementRequest:
    action: MemoryManagementAction
    query: MemoryManagementQuery
    source_request_id: str | None
    is_explicit: bool = True
    has_confirmation: bool = False
    confirmation_token: str | None = None


@dataclass(frozen=True, slots=True)
class MemoryManagementCandidate:
    memory_id: str
    memory_type: MemoryType
    tags: tuple[str, ...]


@dataclass(frozen=True, slots=True)
class MemoryManagementResult:
    status: MemoryManagementStatus
    reason_code: str
    candidates: tuple[MemoryManagementCandidate, ...] = ()
    deleted_memory_ids: tuple[str, ...] = ()
    deleted_count: int = 0
    requires_confirmation: bool = False
    confirmation_token: str | None = None
```

`MemoryManagementCandidate` intentionally excludes memory content, source request identifiers, timestamps, consent levels, status, metadata, and ranking diagnostics. It provides only opaque identity and non-content classification necessary for a caller to narrow a target. A later presentation layer may use a separately authorized inspection operation to show durable content.

`MemoryManagementResult` must never retain deleted content or reconstructable metadata. Returned opaque identifiers and counts are transient operation results, not audit records.

## Inspection and Target Resolution

- `INSPECT` requires an exact `memory_id` and returns an approved, defensive copy of the record through a dedicated typed inspection result. It is not a ranked search.
- `LIST` returns deterministic candidate summaries in ascending `memory_id` order, subject to policy and `maximum_results`.
- `FIND` applies only exact normalized content, type, and tag filters. Text normalization is Unicode casefolding, trimming, and whitespace collapse. Tags use normalized match-any semantics. It performs no semantic, fuzzy, embedding, or LLM matching.
- A query with no `memory_id`, `exact_content`, types, or tags is invalid for `FIND` and `DELETE_MATCHES`; it avoids an accidental equivalent of delete-all.
- `DELETE_ONE` requires one exact `memory_id`. It does not delete a different record because of content matching.
- `DELETE_MATCHES` resolves candidates using the same deterministic `FIND` behavior. The result order is ascending `memory_id`.
- `DELETE_ALL` does not resolve or return individual candidate records before confirmation. It operates on every policy-authorized record only after explicit confirmation.

By default, management inspection, listing, and finding exclude sensitive-confirmed records. `include_sensitive=True` only asks `MemoryPolicy` to evaluate those records; it is never authorization by itself. The proposal leaves the privacy-sensitive choice of whether an explicitly confirmed deletion request may target sensitive records to `MemoryPolicy` approval.

## Confirmation and Deletion Rules

- Every management action requires `is_explicit=True`; otherwise policy rejects it.
- `DELETE_ONE` may execute without a second confirmation only when it names one exact `memory_id` and policy approves it.
- `DELETE_MATCHES` with no matches returns `NO_MATCH`; with one match it requires confirmation before deletion; with more than one match it returns deterministic candidates and requires confirmation.
- `DELETE_ALL` always requires confirmation, even when it would affect one record.
- A confirmation must repeat the same management action and query and set `has_confirmation=True`; it must not expand the resolved scope.
- The initial confirmation-required result provides an opaque confirmation token derived from the resolved opaque identifiers. After confirmation, the manager re-resolves candidates and compares this token. If the target set has changed, it returns `REQUIRES_CONFIRMATION` again rather than deleting a different scope.
- Deletion calls `MemoryStore.delete` for exact identifiers or `MemoryStore.clear` only for an approved delete-all action. The store performs hard deletion with no tombstone or retained content.
- The manager must never attempt rollback after deletion. Recreating a deleted value would violate hard-delete expectations.

## Failure Behavior

No match, policy rejection, and confirmation-required are normal structured outcomes and do not raise an exception.

For multi-record deletion, the manager pre-resolves and policy-checks every target before the first deletion. A backend failure after one or more successful hard deletions returns `PARTIAL` with only the opaque identifiers successfully deleted and a stable non-content error code. It does not roll back. A failure before any deletion returns `FAILED`.

For a missing exact identifier, `DELETE_ONE` returns `NO_MATCH`. A race in which the record disappears after resolution is handled as `FAILED` when no record was deleted or `PARTIAL` when another deletion already succeeded.

# Functional Requirements

- Define provider-neutral management actions, query, candidate, inspection, request, and result contracts.
- Define `MemoryManager` and a policy-controlled reference implementation.
- Extend `MemoryPolicy` with explicit inspection and deletion authorization decisions.
- Keep `MemoryStore` as the physical owner of hard deletion.
- Reuse `MemoryWriter.correct_memory` for corrections; do not create a second correction implementation.
- Use exact deterministic filtering for management discovery, never retrieval ranking or semantic matching.
- Require confirmation for every bulk deletion and every match-based deletion.
- Ensure sensitive records are excluded by default and cannot be accessed merely by setting `include_sensitive=True`.
- Return defensive copies for inspection and non-content candidates for disambiguation.
- Report success, no-match, rejection, confirmation-required, failed, and partial outcomes distinctly.
- Keep operation results free of deleted content, prior values, tombstones, and audit history.

# Acceptance Criteria

- An explicit caller can inspect, list, find, correct, delete one, delete matching, and delete all memory through typed contracts.
- A single exact identifier can be deleted only after policy authorization.
- Match-based and delete-all operations never delete records before explicit confirmation.
- Ambiguous matching returns deterministically ordered, non-content candidates.
- A hard-deleted record cannot be retrieved, inspected, listed, found, restored, or added to Context Assembly.
- A correction continues to preserve `memory_id` and `created_at` while replacing old content through `MemoryWriter`.
- Sensitive records remain excluded by default and policy remains the final authority for access or deletion.
- Multi-delete failures distinguish no deletion, partial hard deletion, and complete success without rollback.
- Tests cover policy decisions, exact filtering, ambiguity, confirmation, hard deletion, sensitive exclusion, mutation safety, no-match, partial failure, and deterministic order.

# Out of Scope

- Natural-language intent detection, UI prompts, voice presentation, or LLM interaction.
- Automatic, inferred, scheduled, or retention-based deletion.
- Deleted-record tombstones, retained deleted content, historical versioning, or audit logs.
- Fuzzy, semantic, embedding, vector, or LLM-assisted matching.
- Home Assistant, EventBus, ConversationManager, external persistence, encryption, multi-user ownership, and Context Assembly changes.

# Approved Decisions

1. `MemoryManager` is the provider-neutral management boundary; `MemoryStore` retains physical deletion and `MemoryWriter` retains correction.
2. Ambiguous deletion exposes opaque, non-content candidates; a separate authorized inspect operation returns record content.
3. Management matching is limited to exact normalized content, type, and tag filters.
4. Match-based and delete-all operations require confirmation and use re-resolution with an opaque scope token.
5. Exact-identifier deletion proceeds without a second confirmation after policy authorization.
6. Sensitive records are excluded by default; inclusion requires `MemoryPolicy` approval and confirmation.
7. Multi-delete failures report partial hard deletion without rollback.
