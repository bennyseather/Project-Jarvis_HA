# Purpose

Plan and coordinate the approved processing path for a request while keeping decision-making distinct from execution and response presentation.

# Background

After a RequestContext is classified, enriched with relevant capabilities, and supplied with assembled context, Jarvis needs an orchestration stage that plans and coordinates the appropriate path. The ExecutionPlanner produces a provider-neutral ExecutionPlan; the ExecutionPipeline performs its ordered steps through injected handlers. This stage must respect the boundaries in ADR-001: Home Assistant remains the system of record and the language model remains responsible for reasoning and language.

# Functional Requirements

- Receive a classified and assembled RequestContext.
- Produce an ExecutionPlan containing a selected capability, selected provider, ordered steps, metadata, confirmation requirement, and reserved parallel-execution flag.
- Execute the plan sequentially through registered step handlers.
- Support plans that require no capability execution.
- Add a structured execution outcome to RequestContext for the response pipeline.
- Report unavailable, unsupported, or unsuccessful execution outcomes without obscuring their status.
- Avoid changing home state unless a later approved capability explicitly performs an authorized action.

# Deliverables

- ExecutionPlan and ExecutionResult models.
- An ExecutionPlanner and ExecutionPipeline.
- A documented step-handler contract.
- A documented execution-outcome contract.
- Tests for successful coordination, no-action paths, unsupported requests, and failure outcomes.

# Acceptance Criteria

- The planner consistently produces a provider-neutral plan from RequestContext.
- The pipeline executes plan steps in order and stores the result on RequestContext.
- The planner and pipeline update RequestContext lifecycle state as planning and execution complete.
- A structured outcome is produced for every completed pipeline path.
- No-action, unavailable, and unsuccessful outcomes are distinguishable.
- The pipeline does not assume ownership of Home Assistant state or language-model reasoning.
- Tests demonstrate each supported outcome category.

# Out of Scope

- Defining request categories.
- Discovering capabilities independently of the discovery stage.
- Constructing the full request context.
- Formatting or delivering the final user-facing response.
- Persistent memory, knowledge-engine, event-timeline, or learning features.

# Dependencies

- M1.1 Request Classification.
- M1.2 Capability Registry.
- M1.3 Request Context.
- M1.4 Context Assembly.
