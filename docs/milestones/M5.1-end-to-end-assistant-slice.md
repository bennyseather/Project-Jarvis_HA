# Purpose

Define the first usable Project Jarvis vertical slice: receive one user request, assemble bounded Jarvis context, obtain language-model reasoning, invoke an explicitly approved Home Assistant capability when needed, and return a structured response.

## Implementation Status

Approved and implemented with injected provider contracts and deterministic fake-provider coverage. The orchestrator accepts conversation and one allow-listed, read-only entity-state proposal only; it does not expose state-changing Home Assistant execution.

# Background

EPIC 1 provides the orchestration framework. EPIC 2 Memory and EPIC 3 Knowledge provide optional context sources. Jarvis is not yet a usable Home Assistant AI agent because these parts are not connected to a real request path, language-model provider, or Home Assistant capability execution.

This milestone must prove the system boundary rather than broaden it. Home Assistant remains the owner of devices, entities, state, and service execution. The language model remains the owner of language understanding and reasoning. Jarvis owns request coordination, bounded context assembly, capability selection, confirmation handling, and persistent context.

# Proposed Architecture

## Supported Initial Path

Support one request class at a time:

- Conversational or informational requests receive a language-model response using bounded Jarvis context.
- A single explicitly supported Home Assistant read-only query may use an approved Home Assistant provider and return its structured result to the language model for presentation.
- Home Assistant state-changing commands are not enabled in the first slice.

The initial Home Assistant operation should be one read-only, allow-listed query, such as retrieving the current state of a known entity. Entity resolution must use Home Assistant as the system of record and must not maintain an independent Jarvis entity database.

## Flow

```text
RequestContext
  -> classification
  -> capability selection
  -> Context Assembly (Memory and Knowledge optional)
  -> bounded prompt/input construction
  -> language-model provider reasoning
  -> optional allow-listed read-only Home Assistant query
  -> structured Response
```

The language model returns a provider-neutral proposed action or conversational outcome. Jarvis validates that proposal against the selected capability, allow list, and confirmation policy before calling Home Assistant. The model never receives credentials and cannot directly invoke tools.

## Provider Contracts

- `LanguageModelProvider`: accepts a typed, bounded request package and returns a typed provider-neutral reasoning result. It does not access Home Assistant directly.
- `HomeAssistantProvider`: exposes one typed read-only query for explicitly allowed entities. It owns communication with Home Assistant and returns current state as supplied by Home Assistant.
- `AssistantOrchestrator`: coordinates the existing RequestContext lifecycle, invokes injected providers, validates actions, and maps outcomes to the existing response pipeline.
- `Prompt/Input Builder`: converts only approved RequestContext fields into a bounded provider input. It excludes credentials, internal metadata, source request identifiers, opaque memory/knowledge IDs, and arbitrary storage metadata.

## Safety and Confirmation

- No Home Assistant state-changing service call is enabled in M5.1.
- Only one configured allow-listed read-only Home Assistant operation is executable.
- Home Assistant errors, unavailable entities, unsupported model proposals, and provider failures produce structured non-success outcomes.
- The language-model provider cannot bypass capability selection, Home Assistant allow lists, or Jarvis confirmation policy.
- Memory and Knowledge are optional; their absence cannot prevent a normal conversational response.

# Functional Requirements

- Define typed provider-neutral contracts for language-model reasoning input and output.
- Define one injected Home Assistant read-only provider contract and one allow-listed operation.
- Wire the existing classification, capability, context, execution, and response components through an `AssistantOrchestrator`.
- Build bounded input from original request, approved context, and explicitly supplied Home Assistant result only.
- Support direct conversation and one successful read-only Home Assistant query path.
- Return structured responses for success, unavailable, unsupported, and provider-failure outcomes.
- Use injectable providers and deterministic fakes for tests.

# Acceptance Criteria

- A test request completes from RequestContext creation through structured Response.
- Memory and Knowledge are included only when configured and bounded.
- A model proposal cannot execute an unselected or non-allow-listed Home Assistant operation.
- The only Home Assistant operation is read-only and uses Home Assistant as the source of truth.
- No state-changing service, autonomous automation, credential exposure, direct model-to-Home-Assistant access, or duplicate entity registry is introduced.

# Out of Scope

- Home Assistant commands, automations, service calls, or state-changing actions.
- Multi-tool planning, autonomous task execution, voice UI, streaming, conversation history management, user authentication, and production secrets management.
- Event Timeline, Learning, document import, embeddings, semantic search, and persistent external Knowledge storage.

# Dependencies

- EPIC 1 Orchestration Framework.
- EPIC 2 Memory Foundation.
- EPIC 3 Knowledge Foundation.
- Existing Home Assistant and language-model provider configuration.

# Approval Decisions Required

1. Approve a narrow first slice containing conversation plus one allow-listed read-only Home Assistant query.
2. Approve no Home Assistant state-changing capability in M5.1.
3. Approve typed provider-neutral contracts and injected fakes for the language model and Home Assistant.
4. Approve the proposed validation boundary: model proposals are validated by Jarvis before any Home Assistant call.
5. Approve bounded prompt/input construction that excludes credentials and internal persistence metadata.
