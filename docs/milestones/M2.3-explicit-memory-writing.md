# Purpose

Implement the policy-controlled path for explicit user-requested memory creation and correction.

# Background

M2.2 provides storage mechanics without deciding what may be stored. M2.3 adds MemoryPolicy and MemoryWriter boundaries so only approved explicit requests reach MemoryStore. It does not extract intent, retrieve memory, or integrate with orchestration.

# Functional Requirements

- Define typed contracts for explicit creation requests, correction requests, policy decisions, and write outcomes.
- Define a provider-neutral MemoryPolicy that evaluates creation and correction requests.
- Approve only explicit, non-sensitive preference, fact, instruction, and project memory.
- Return a confirmation-required outcome for sensitive requests that lack confirmation.
- Reject implicit, inferred, invalid-source, and reserved-type requests.
- Create records only after policy approval and preserve provenance and source request correlation.
- Correct records by preserving `memory_id` and `created_at`, setting a new `updated_at`, and replacing prior content.

## Correction Field Semantics

Correction requests use the public `UNSET` sentinel for every optional field.

- `UNSET` preserves the currently stored value.
- Any provided value replaces the stored value.
- Explicit `None` clears nullable fields such as `expires_at`, `importance`, and `confidence`.
- Empty collections such as `tags=()` and `metadata={}` replace stored collections with empty collections.

# Deliverables

- Explicit-memory and correction request contracts.
- MemoryPolicy protocol and deterministic ExplicitMemoryPolicy.
- MemoryWriter protocol and policy-controlled reference implementation.
- MemoryWriteResult contract.
- Unit tests for creation, rejection, confirmation, correction, provenance, deterministic factories, and `UNSET` semantics.

# Acceptance Criteria

- Approved explicit eligible memory is stored with deterministic identity and timestamps.
- Rejected and confirmation-required operations do not modify MemoryStore.
- Reserved memory types are not actively written.
- Corrections preserve identity and creation time while replacing prior content.
- Omitted, replaced, cleared, and emptied optional correction fields follow the documented `UNSET` contract.
- No LLM, Home Assistant, retrieval, ranking, context-assembly, or user-interface behavior is implemented.

# Out of Scope

- Natural-language intent detection and orchestration integration.
- Inferred memory, automatic summaries, and interactive confirmation flow.
- Retrieval, search, semantic ranking, embeddings, and Context Assembly integration.
- Deletion workflows, external persistence, encryption, multi-user ownership, audit logging, Home Assistant, LLM, and ConversationManager changes.

# Dependencies

- M2.1 Memory Contracts and Policy.
- M2.2 In-Memory Store.
- ADR-003 Memory Architecture, Privacy, and Lifecycle.
