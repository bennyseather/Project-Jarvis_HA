# Purpose

Integrate approved, policy-controlled memory retrieval into Context Assembly without exposing storage implementation details or making memory required for every request.

## Implementation Status

Approved and implemented. `MemoryContextProvider` is the only M2.5 integration point. It depends on `MemoryRetriever`, requests a maximum of five non-sensitive results by default, and returns the typed `MemoryContext` contract. The complete unit suite passed after implementation.

# Background

M2.4 provides a provider-neutral `MemoryRetriever` that returns ranked, policy-eligible `MemoryMatch` values. Context Assembly currently accepts independently supplied `ContextPackage` values, but its `memory` section is an untyped mapping and does not yet invoke retrieval. This milestone should establish a typed, bounded context representation and a context provider that depends only on the `MemoryRetriever` protocol.

# Proposed Architecture

## Typed Context Shape

Replace the untyped `ContextPackage.memory: Mapping[str, object] | None` field with `MemoryContext | None` in the M2.5 implementation. The proposed types are:

```python
@dataclass(frozen=True, slots=True)
class MemoryContextMatch:
    content: str
    memory_type: MemoryType
    tags: tuple[str, ...]
    source: MemorySource
    retrieval_score: float


@dataclass(frozen=True, slots=True)
class MemoryContext:
    matches: tuple[MemoryContextMatch, ...]
    result_limit: int
```

`MemoryContextMatch` deliberately carries only information useful to a later reasoning or presentation layer:

| Field | Included | Rationale |
| --- | --- | --- |
| `content` | Yes | This is the approved durable information relevant to the request. |
| `memory_type` | Yes | Lets downstream orchestration distinguish preferences, facts, instructions, and projects. |
| `tags` | Yes | Supplies approved, user- or system-approved categorization. |
| `source` | Yes | Retains minimal provenance: explicit request or correction. |
| `retrieval_score` | Yes | Preserves the deterministic relevance signal without exposing ranker internals. |
| `memory_id` | No | Opaque storage identity is not needed for contextual reasoning. Explicit memory-management capabilities can retrieve it independently when approved. |
| `source_request_id` | No | Internal correlation data is not useful in context and could reveal unrelated request structure. |
| `created_at` / `updated_at` / `expires_at` | No | Recency and expiry are already applied by retrieval; raw timestamps are not needed in the initial context contract. |
| `importance` / `confidence` | No | These are ranking inputs and are represented by `retrieval_score`; exposing them would overstate their current meaning. |
| `consent_level` / `status` | No | Policy must enforce these before records enter context. |
| `metadata` | No | Arbitrary backend metadata is not approved for general context exposure. |
| score breakdown / match reasons | No | Internal ranking diagnostics belong to retrieval tests and inspection tools, not the default request context. |

The memory section is absent (`None`) when no memory provider is configured. When a provider is configured but no records are eligible or match, it returns `MemoryContext(matches=(), result_limit=...)`. This distinguishes unavailable memory from an intentionally empty retrieval result without exposing policy-denial details.

## Provider Boundary

Introduce a `MemoryContextProvider` that implements the existing `ContextProvider` protocol and is injected with a `MemoryRetriever`. It translates `RequestContext` into a `MemoryRetrievalQuery`, calls `MemoryRetriever.retrieve`, and converts the returned matches to `MemoryContextMatch` values.

The provider must not import or depend on `MemoryStore`, `MemoryRanker`, `PolicyControlledMemoryRetriever`, or a specific storage backend. It must not reapply ranking, filtering, lifecycle, or consent logic. It must rely on the retriever's policy-controlled result.

The query should carry the original request text and request identifier where available. Initial M2.5 must use `include_sensitive=False` unconditionally. A future authorization decision may allow an explicitly approved caller to request sensitive context, but that decision remains with `MemoryPolicy`; no Context Assembly flag is an authorization bypass.

## Bounded Results

The proposed Context Assembly limit is a default of 5 matches and an absolute maximum of 10. `MemoryContextProvider` supplies this limit to the retrieval query and defensively rejects a configured value outside `0..10`.

Five results is sufficient for the initial prompt/context budget while leaving M2.4's maximum of ten available to explicit memory-management interfaces. A limit of zero is valid and produces an empty `MemoryContext` without ranking.

## Failure Behavior

No result, policy-denied records, and query-filtered records are normal outcomes. They produce an empty `MemoryContext` and do not alter request lifecycle behavior.

An unavailable or failing memory provider is an infrastructure failure, not an empty result. Under the existing `ContextAssembler` contract, it propagates from `MemoryContextProvider`, marks `RequestContext` as `FAILED`, and prevents a partial context package from being treated as fully assembled. This keeps failure behavior consistent with every other context provider. A future resilience decision may introduce explicitly optional providers and structured degradation metadata, but that is not part of M2.5.

# Functional Requirements

- Define the `MemoryContext` and `MemoryContextMatch` contracts in the context-model layer.
- Change `ContextPackage.memory` to use `MemoryContext | None`.
- Implement a provider that depends only on `MemoryRetriever` and returns a partial `ContextPackage`.
- Derive its retrieval query from the original request and correlation identifier in `RequestContext`.
- Request no more than five records by default and never more than ten.
- Use `include_sensitive=False` for all initial Context Assembly retrieval.
- Convert only the approved fields listed above into the context contract.
- Preserve retrieval order and scores exactly as returned; do not rerank or filter records again.
- Return an empty `MemoryContext` for normal empty retrieval outcomes.
- Allow retriever failures to follow the existing ContextAssembler failure path.
- Preserve deterministic assembly order and existing merge behavior for other context sections.

# Acceptance Criteria

- Context Assembly can receive memory through a `MemoryRetriever` without depending on any concrete memory backend.
- A populated context contains only the approved typed memory fields.
- Context Assembly never requests sensitive memory by default.
- A configured provider produces an empty typed memory context when no record is available.
- Memory retrieval results are bounded to the approved context limit.
- A retrieval failure marks the request as failed through existing ContextAssembler behavior.
- Tests demonstrate populated, empty, bounded, sensitive-excluded, deterministic, and failure outcomes.
- M2.5 introduces no memory writes, corrections, deletions, automatic persistence, summaries, inference, embeddings, semantic search, Home Assistant calls, or LLM calls.

# Out of Scope

- Memory writing, correction, deletion, or inspection workflows.
- Authorization or interactive confirmation for sensitive-memory retrieval.
- Retrieval ranking changes or semantic retrieval.
- Optional-provider degradation and partial-assembly resilience.
- Prompt construction, language-model interaction, ConversationManager integration, or Home Assistant integration.
- EventBus, audit logging, external persistence, and multi-user ownership.

# Dependencies

- M1.3 Request Context.
- M1.4 Context Assembly.
- M2.1 Memory Contracts and Policy.
- M2.4 Memory Retrieval.
- ADR-003 Memory Architecture, Privacy, and Lifecycle.

# Approved Decisions

1. `ContextPackage.memory` uses the typed `MemoryContext` model.
2. Context exposes only content, type, tags, source, and retrieval score; opaque identifiers, request correlations, timestamps, consent/status, metadata, and score diagnostics remain internal.
3. Context Assembly requests five memory matches by default and permits no more than ten.
4. Context Assembly always retrieves with `include_sensitive=False` in this milestone.
5. A memory-provider failure follows the existing Context Assembly failure lifecycle.
