# Purpose

Connect the existing OpenAI and Home Assistant clients to the M5.1 provider-neutral contracts without allowing direct model-to-tool access or Home Assistant state changes.

# Background

M5.1 supplies tested contracts and a safe allow-listed orchestrator using fakes. M5.2 introduces production adapters around the existing OpenAI and Home Assistant clients. The adapters translate data only; policy, allow-list validation, orchestration, and response decisions remain in Jarvis.

# Proposed Architecture

## Language-Model Adapter

Implement `OpenAIAssistantProposalProvider`, adapting the existing `OpenAIProvider` to `LanguageModelProvider`.

It receives `AssistantInput` containing bounded request text and approved context only. It constructs an explicit provider input instructing the model to return one typed proposal:

- `conversation` with a message, or
- `read_entity_state` with one entity identifier.

The adapter validates the model output against the typed proposal schema. Malformed or unsupported output becomes a provider-neutral failure/unsupported outcome; it never becomes a Home Assistant call. Credentials remain inside `OpenAIProvider` and are never included in model input.

## Home Assistant Read Adapter

Implement `HomeAssistantReadAdapter`, adapting `HomeAssistantClient` to `HomeAssistantReadProvider`.

It provides only `read_entity_state(entity_id)`. It obtains the current entity state from Home Assistant's read-only state response and returns a typed `HomeAssistantState`. It does not call `call_service`, modify state, load a Jarvis-owned entity registry, or expose raw client messages.

The adapter may cache no state in M5.2. Every read is sourced from Home Assistant at execution time.

## Composition

Add one explicit composition function or application factory that injects:

- OpenAI proposal provider,
- Home Assistant read adapter,
- configured allow-listed entity identifiers,
- existing bounded context assembly components.

The application startup path must not execute a Home Assistant service or a demonstration conversation automatically. It may verify connectivity through existing read-only authentication and state-fetch mechanics only.

# Functional Requirements

- Adapt existing clients to the M5.1 provider protocols.
- Validate all model proposals before returning them to `AssistantOrchestrator`.
- Read a single entity's current state through Home Assistant only.
- Return structured unavailable/failure outcomes when OpenAI, Home Assistant, or an entity is unavailable.
- Add deterministic adapter tests using fake OpenAI and Home Assistant clients.
- Keep allow-list enforcement in `AssistantOrchestrator`.

# Acceptance Criteria

- A composed application can execute a conversational proposal and one allow-listed entity-state query using adapters.
- The LLM adapter never receives credentials or direct Home Assistant access.
- The Home Assistant adapter never invokes `call_service`.
- The model cannot cause an entity read unless the orchestrator allow list approves it.
- Startup performs no state-changing demonstration action.

# Out of Scope

- State-changing Home Assistant actions, service calls, automations, or multi-tool plans.
- Streaming, voice, external document retrieval, user authentication, production secrets redesign, and conversation-history management.

# Dependencies

- M5.1 Safe Read-Only Assistant Slice.
- Existing `OpenAIProvider` and `HomeAssistantClient`.
- ADR-001 Project Scope.

# Approval Decisions Required

1. Approve the OpenAI adapter returning only schema-validated typed proposals.
2. Approve a Home Assistant adapter limited to current single-entity read operations.
3. Approve no state cache and no service call in M5.2.
4. Approve explicit application composition with allow-listed entity identifiers.
